# Part 2 stage 0: project setup and first deploy, implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** an empty Worker with every binding the design needs, both D1 schemas, tests in the Workers runtime and a CI workflow that deploys from `main`, so that `GET /healthz` on the deployed URL returns the deployed commit.

**Architecture:** one Worker (`src/index.ts`) exports `fetch` (Hono app), `queue` and `scheduled`. Bindings: two D1 databases (facts, MVP events), one Queue with a dead letter queue, one R2 bucket, one Analytics Engine dataset. Tests run in workerd through `@cloudflare/vitest-plugin` with both D1 schemas applied from `migrations/`.

**Tech Stack:** TypeScript 5.9, pnpm 10, Hono 4, Zod 4, wrangler 4.157, vitest 4 with `@cloudflare/vitest-plugin`, oxlint, oxfmt, GitHub Actions.

**Spec:** [part2-mvp-stages.md](part2-mvp-stages.md), section "Stage 0" and the decisions table. Schema source: [data-model.md](../design/data-model.md), "Tables in the D1 facts database" and "MVP events database". Event path: [ADR 0005](../adr/0005-event-ingestion-and-buffering.md).

## Global Constraints

- Everything committed is in English. README prose goes through the `humanizer` skill.
- No account id, API token, real email or other personal data in any committed file. Test data uses `@example.com` only. The account id reaches CI only as the `CLOUDFLARE_ACCOUNT_ID` repository secret.
- Test names say in words what is checked and start with the requirement id: `DLV-1 healthz returns the commit sha`.
- Test files sit under their level, as part2-mvp-stages.md "Test levels" fixes it: `tests/unit/` for pure functions, `tests/integration/` for anything through the Workers runtime. Both tests in this stage are integration tests.
- One Worker for every entry point. Raw SQL, no ORM. `Env` is generated by `wrangler types`, never hand-written; the default export uses `satisfies ExportedHandler<Env>`.
- Secrets never go into `wrangler.jsonc` or source. Non-secret config goes in `vars`.
- Run wrangler through the project's version: `pnpm exec wrangler ...`.
- Exact versions, pinned without ranges: `hono` 4.13.16, `zod` 4.6.7, `wrangler` 4.157.0, `vitest` 4.1.12, `@cloudflare/vitest-plugin` 1.5.1, `typescript` 5.9.3, `oxlint` 1.91.0, `oxfmt` 0.76.0. Node 24, `packageManager` `pnpm@10.3.0`.
- Work happens on branch `part2-stage-0`. Each task commits there. Nothing is pushed until Arthur approves the stage.

## Known setup traps (found in a spike on 2026-11-04, then reverted)

- `@cloudflare/vitest-pool-workers` is renamed to `@cloudflare/vitest-plugin`. The new package exports `cloudflareTest()` (a Vite plugin) and `readD1Migrations()` from its root; there is no `/config` entry. Its test types are at `@cloudflare/vitest-plugin/types`.
- The workerd binary bundled with the test plugin rejects a `compatibility_date` newer than it knows. `2026-11-03` works with plugin 1.5.1; a newer date fails at test start with "requires compatibility date ...".
- `ProvidedEnv` is gone. Test-only bindings are declared by augmenting `Cloudflare.Env` in `declare global { namespace Cloudflare { interface Env { ... } } }`.
- `.agents/` and `.claude/` hold third-party `*.test.cjs` files; vitest must include only `tests/**/*.test.ts`.
- `vitest.config.ts` uses Node APIs; keep it out of the `tsc` program rather than adding Node types.
- pnpm 10 blocks install scripts: `esbuild` and `workerd` must be listed in `pnpm.onlyBuiltDependencies`.

## Review Focus

- CI checks out a tree without `worker-configuration.d.ts` (it is gitignored): `pnpm typecheck` must generate it first, or CI fails where the laptop passes. Task 1 makes `typecheck` run `wrangler types` before `tsc`.
- A migration that fails remotely must stop the deploy, so the Worker never runs against a schema it does not expect. Task 3 orders migrations before deploy in one job, with no `continue-on-error`.
- A missing `CLOUDFLARE_API_TOKEN` or `CLOUDFLARE_ACCOUNT_ID` secret must fail the deploy job visibly, not deploy to a default account. Task 3 passes both as job env from secrets only.
- The schema in `migrations/facts/0001_init.sql` must match data-model.md exactly; a drifted column breaks stage 1 silently. Task 2 copies the eight `CREATE TABLE` blocks verbatim and tests the table list.
- `/healthz` must not leak anything but the sha (no env dump, no binding names). Task 1's test asserts the whole body equals `{ sha }`.

Write `migrations/events/0001_init.sql`: one table `events` with `event_id TEXT NOT NULL PRIMARY KEY` (SQLite allows NULL in a TEXT primary key, and NULLs never conflict, so without `NOT NULL` an event without an id would slip past `ON CONFLICT (event_id) DO NOTHING`), `schema_version INTEGER`, `type TEXT`, `client_time INTEGER` (nullable), `received_at INTEGER`, `user_id TEXT` (nullable), `visit_id TEXT`, `seq INTEGER` (nullable), `prelander_id TEXT`, all `NOT NULL` except `client_time`, `seq` and `user_id`. data-model.md's envelope table makes `client_time` and `seq` null for server events (`offer_selected`, `offer_click`, `lead`, `purchase` in stage 2 and 3); `user_id` is null for `lead` and `purchase` whose click lost its user (deletion or the 90-day cleanup), because a NOT NULL there would fail the loader's whole batch into the dead letter queue. The last column is `payload TEXT NOT NULL CHECK (json_valid(payload))`; a header comment saying it is the MVP stand-in for BigQuery (ADR 0005) and is removed when the loader targets BigQuery.
