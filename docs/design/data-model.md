# Data model and event catalog

This file lists every table, every event type and every key the design relies on, and traces the demo scenario through them. The reasoning behind each store is in the ADRs; this file is the reference for what the stores hold.

There are two kinds of data. Facts are what the rules read on the live path: the user, the current answers, clicks, Leads and Purchases, the offer catalog and the partners. They live in one D1 database and are written synchronously ([ADR 0003](../adr/0003-operational-store.md), P-1). Events are the analytics record of everything that happened. They travel through the Queue into files in R2 and then into BigQuery ([ADR 0005](../adr/0005-event-ingestion-and-buffering.md), [ADR 0006](../adr/0006-bigquery-delivery.md)), and the rules never read them.

## What this file settles

These points refine the ADRs. Where the wording differs, this file is the current one; the ADRs keep their text until they are accepted, and any change after acceptance goes into a new ADR.

1. Answers and email reach D1 in one request at quiz completion, `POST /api/complete`. Per-step answers go to `POST /api/events` as analytics only and never touch D1. This refines ADR 0003, which described answers written one at a time.
2. The ordering key for the latest accepted answer in D1 is the server receive time of the completion request, `received_at`. ADR 0003 called the column `answered_at` and defined the key as receive time plus the per-visit sequence; the sequence is no longer needed in D1 because one request carries the final state of the quiz (R-3, R-10, Q-4).
3. A new user causes no D1 write at entry. The `users` row is created at completion. A user who leaves before the email step has no rows in D1, only events in BigQuery. This refines ADR 0003 and ADR 0004.
4. The 90-day cleanup measures a user's last activity as the later of the last completion and the last click, because entry no longer writes anything. ADR 0003 said "last visit and last click".
5. The partner that owns an offer is a column of `offers`. ADR 0007 put a list of offer IDs on the partner row.
6. `prelander_id` is taken from the request, as sent by the client (ADR 0005). A signed visit token was considered and deferred (see "Boundaries and deferred options").
7. `visit_id` is generated by the Worker at `GET /p/{prelander}`, because the Worker emits the first event of the visit, and is written into the rendered page; the browser puts it on every event of that page load. ADR 0005 left the source of `visit_id` open.
8. Three tables and a few columns have different names here than in the ADRs:

| Name in the ADRs | Name here |
|---|---|
| `postbacks` (ADR 0003, ADR 0007) | `conversions` |
| `postback_quarantine` (ADR 0007) | `quarantine` |
| `catalog_versions` (ADR 0003) | `catalog_history` |
| `user_answers.answered_at` (ADR 0003) | `user_answers.received_at` |
| `offers.offer_id` (ADR 0003) | `offers.id` |
| `partners.partner_id`, `secret_current`, `secret_previous` (ADR 0007) | `partners.id`, `secret_current_enc`, `secret_previous_enc` |
| offer IDs on the partner row (ADR 0007) | `offers.partner_id` |

## Requests and what they touch

| Request | Reads in D1 | Writes in D1 | Events emitted |
|---|---|---|---|
| `GET /p/{prelander}`, no cookie | nothing | nothing | `prelander_viewed` (`quiz`) |
| `GET /p/{prelander}`, with cookie | `users`, `user_answers`, `conversions` joined with `clicks`, current `offers` | `clicks` when entry selection redirects | `prelander_viewed`; when entry selection returns an offer or `no_offer` also `offer_selected` (`entry`), and on a redirect `offer_click` |
| `POST /api/events` | nothing | nothing | the one event in the body |
| `POST /api/complete` | `conversions` joined with `clicks`, current `offers` | `users`, `user_answers` | `quiz_completed`, `offer_selected` (`completion`) |
| `GET /go?prelander=&visit=` | `users`, `user_answers`, `conversions` joined with `clicks`, current `offers` | `clicks` when selection returns an offer | `offer_click` when a click is written |
| `POST /postback/v1/{partner}` | `partners`, `clicks`, `offers` of the click's version | `conversions`, or `quarantine` | `lead` or `purchase` when accepted or duplicate |
| Cleanup job, daily | `users`, `clicks`, `conversions` | deletes from `users`, `user_answers`, `clicks` | none |

Entry for a user with a cookie reads the facts in one D1 batch. A cookie without a `users` row (a user who left before completion) finds nothing and gets the quiz. An existing user without any Lead also gets an empty quiz (Q-1, ADR 0004). A user whose Leads are all for disabled offers and whose answers are sufficient skips the quiz under rule 3 (OFF-9), so entry can redirect with reason `best_epu` or `fallback_universal` as well as `lead_return`.

### Quiz completion

The browser sends the final state of the quiz in one request:

```
POST /api/complete
Content-Type: application/json

{"visit_id": "V1", "prelander_id": "P1",
 "answers": {"gender": "women", "ethnicity": "asia"},
 "email": "u1@example.com"}
```

`visit_id` and `prelander_id` are there so the server events of this request carry the same visit and prelander as the browser's step events. The Worker then:

1. takes the UserID from the cookie (ADR 0002) and ignores any user id in the body;
2. validates each answer against the prelander's quiz flow config (one JSON file per prelander listing the steps with their question key, allowed values, wording and next step) and the email against a format check (Q-5); a failure answers `400` and writes nothing;
3. in one D1 batch, which runs as a transaction: upserts the `users` row with the encrypted email, upserts one `user_answers` row per answer, and reads the user's Leads and the current catalog;
4. runs `select(facts, catalog, "completion")` (ADR 0004);
5. sends `quiz_completed` and `offer_selected` to the Queue;
6. answers `{"offer_id": "003", "name": "Asia Connect", "url": "https://asia-connect.example", "reason": "best_epu", "catalog_version": 1}`.

The send does not delay the answer. If the Queue refuses an event, `sendEvent()` writes it to R2 `pending/`; if R2 refuses it too, the endpoint still answers `200` and that event is lost. The page never waits for analytics (NFR-4). Only `POST /api/events` and postbacks answer `503` when both refuse, because the browser and the partner can resend.

The step events of the same visit still go to `POST /api/events`, one event per request (Arthur's decision of 2026-11-02, ADR 0005). They feed analytics and are never written to D1.

## Tables in the D1 facts database

Times are `INTEGER` Unix milliseconds in UTC. Enumerated values such as `type`, `reason` and `ethnicity` are validated by the Worker and the catalog script, not by `CHECK` constraints, because changing a `CHECK` in SQLite means rebuilding the table, which the additive migration rule forbids. `CHECK` is used only for rules that will not change: valid JSON and 0/1 flags. D1 enforces foreign keys by default.

### users

```sql
CREATE TABLE users (
  id                TEXT PRIMARY KEY,   -- UserID from the identity cookie
  email_enc         TEXT NOT NULL,      -- AES-GCM ciphertext, "v1:<iv>:<ciphertext>" in base64
  email_hash        TEXT NOT NULL,      -- HMAC-SHA256 of the trimmed, lower-cased email, hex
  created_at        INTEGER NOT NULL,
  last_completed_at INTEGER NOT NULL
);
CREATE INDEX users_email_hash ON users (email_hash);
```

- Put there by ADR 0002 (UserID) and ADR 0003 (facts in D1); email handling from P-5.
- Written at quiz completion, as an upsert: `INSERT ... ON CONFLICT (id) DO UPDATE SET email_enc = excluded.email_enc, email_hash = excluded.email_hash, last_completed_at = excluded.last_completed_at WHERE excluded.last_completed_at > users.last_completed_at`. A user who completes the quiz twice keeps the email of the later completion.
- Read at entry (does the user have facts), by the cleanup job and by deletion requests.
- The index on `email_hash` is not unique: two browsers can enter the same email, and they stay two users, because an email is not identity (ID-3, Q-19). The hash is used for deletion requests and never to merge or recognise users.
- The `v1:` prefix names the master key, so the key can be rotated by re-encrypting rows under `v2:` while both are readable.

### user_answers

```sql
CREATE TABLE user_answers (
  user_id      TEXT NOT NULL REFERENCES users (id) ON DELETE CASCADE,
  question_key TEXT NOT NULL,                      -- "gender", "ethnicity"
  value        TEXT NOT NULL CHECK (json_valid(value)),
  received_at  INTEGER NOT NULL,                   -- receive time of the completion request
  PRIMARY KEY (user_id, question_key)
);
```

- Put there by ADR 0003. One row per question, holding the latest accepted answer. A new question is a new `question_key` and needs no migration.
- `value` is JSON text: `"women"` is stored as the JSON string `"\"women\""`, so a later question can take a number, an array or an object.
- Written at completion:

```sql
INSERT INTO user_answers (user_id, question_key, value, received_at)
VALUES (?1, ?2, ?3, ?4)
ON CONFLICT (user_id, question_key) DO UPDATE
  SET value = excluded.value, received_at = excluded.received_at
  WHERE excluded.received_at > user_answers.received_at;
```

- Read at entry and at completion, as part of the facts for `select()`.

### partners

```sql
CREATE TABLE partners (
  id                  TEXT PRIMARY KEY,   -- appears in /postback/v1/{partner_id}
  name                TEXT NOT NULL,
  active              INTEGER NOT NULL CHECK (active IN (0, 1)),
  secret_current_enc  TEXT NOT NULL,      -- AES-GCM under the master key
  secret_previous_enc TEXT                -- set during rotation, cleared after it
);
```

- Put there by ADR 0007. Adding a partner is one row and one secret, with no deploy.
- Written by an operator script. Read by the postback endpoint to check the signature with the current or the previous secret.

### catalog_history

```sql
CREATE TABLE catalog_history (
  version    INTEGER PRIMARY KEY,
  created_at INTEGER NOT NULL,
  changed_by TEXT NOT NULL,
  note       TEXT
);
```

- Put there by ADR 0003 and P-3. One row per catalog change. The current version is `MAX(version)`.
- Written by the catalog script. Read by every selection, to find the current version.

### offers

```sql
CREATE TABLE offers (
  version    INTEGER NOT NULL REFERENCES catalog_history (version),
  id         TEXT NOT NULL,                       -- "001" ... "007"
  partner_id TEXT NOT NULL REFERENCES partners (id),
  name       TEXT NOT NULL,
  ethnicity  TEXT NOT NULL,                       -- asia | europe | latam | any
  genders    TEXT NOT NULL CHECK (json_valid(genders)),  -- ["women","men"]
  epu        REAL NOT NULL,
  url        TEXT NOT NULL,
  kind       TEXT NOT NULL,                       -- specialised | universal
  active     INTEGER NOT NULL CHECK (active IN (0, 1)),
  PRIMARY KEY (version, id)
);
```

- Put there by ADR 0003. Version 1 is the spec's catalog of seven offers, all active (OFF-1).
- Every version is a full copy of all offers (P-3). The catalog script inserts the `catalog_history` row and the copied offer rows, with the change applied, in one D1 batch, so selection never sees half a version. If two scripts run at the same time, both try to insert the same version number and the primary key rejects the second one.
- Read at entry, at completion and at `/go` (current version), and by the postback endpoint (the version recorded on the click).
- A full copy per version instead of a diff: with seven offers a version is a few kilobytes, and reading the catalog that explains a past redirect is `WHERE version = ?` with nothing to replay. A diff would make every read of an old version rebuild it from the history.
- `kind` is a column instead of being derived from `ethnicity = 'any'`: the universal offer has a different rule (it is used only when nothing specialised matches and never competes on EPU, OFF-6, OFF-7), and a rule should not hang on a data value that someone may later reuse for an ordinary offer. Q-7 asks whether there can be more than one universal offer; with a column, the answer is a data change.

### clicks

```sql
CREATE TABLE clicks (
  click_id        TEXT PRIMARY KEY,            -- random, unguessable
  user_id         TEXT REFERENCES users (id) ON DELETE SET NULL,
  offer_id        TEXT NOT NULL,
  catalog_version INTEGER NOT NULL,
  prelander_id    TEXT NOT NULL,
  visit_id        TEXT NOT NULL,
  reason          TEXT NOT NULL,               -- best_epu | fallback_universal | lead_return
  created_at      INTEGER NOT NULL,
  FOREIGN KEY (catalog_version, offer_id) REFERENCES offers (version, id)
);
CREATE INDEX clicks_user ON clicks (user_id);
CREATE INDEX clicks_created_at ON clicks (created_at);  -- the cohort view reads clicks by day
```

- Put there by ADR 0003 and ADR 0007 (P-2). The composite key to `offers` also ties the click to a row of `catalog_history`, through `offers.version`.
- Written in two places, always before the `302` is sent (R-6):
  - `GET /go?prelander=P1&visit=V1`, when the user presses the offer button. The URL names no offer. The Worker reads the user's facts and the current catalog version in one batch and runs `select()` again (decision 1 of the [stage 3 plan](../plans/part2-stage-3-redirect-postbacks.md)), so nothing in the link can choose the offer. The click is written for the result, and its reason is the selection's reason: `lead_return`, `best_epu` or `fallback_universal`. An offer turned off since the page was shown is never sent to, because the press gets the new result (R-9, OFF-9). No second `offer_selected` is emitted: `offer_click` carries the offer, the catalog version and the reason. If the result is `no_offer`, no click is written and the page shows the no-offer message (OFF-8). A user without answers or Leads, such as a new cookie, gets a `302` to `/p/{prelander}` and no click (Q-30).
  - `GET /p/{prelander}`, when entry selection redirects. A Lead return is a new transition with a new click ID (Q-21). The same applies to a rule 3 redirect at entry.
- `click_id` carries at least 128 random bits (the IDs in this file are shortened for reading). The partner gets it in the redirect URL, under the parameter name the partner supports (Q-6), and sends it back in the postback. The UserID never leaves the system (ADR 0002, R-11, R-12).
- `prelander_id` and `visit_id` are on the click so that a Lead or Purchase can be attributed to the prelander of the click it references (Q-22) without reading events.
- `user_id` is nullable with `ON DELETE SET NULL` so that a deletion request can remove the user while the click, and the conversions that point at it, stay as unlinked records.
- Clicks are not deduplicated. A double click on the link gives two clicks; the partner sends back whichever ID it received. Offer transition metrics count unique users per offer (AN-4).

### conversions

```sql
CREATE TABLE conversions (
  id              INTEGER PRIMARY KEY,
  partner_id      TEXT NOT NULL REFERENCES partners (id),
  type            TEXT NOT NULL,              -- lead | purchase
  transaction_id  TEXT NOT NULL,
  click_id        TEXT NOT NULL REFERENCES clicks (click_id),
  occurred_at     INTEGER NOT NULL,           -- partner's time, from the body
  accepted_at     INTEGER NOT NULL,           -- our receive time
  payout          REAL,
  currency        TEXT,
  partner_user_id TEXT,                       -- optional contract field, kept for Q-19
  UNIQUE (partner_id, type, transaction_id)
);
CREATE INDEX conversions_click ON conversions (click_id);
CREATE INDEX conversions_type_accepted ON conversions (type, accepted_at);  -- the postback view reads by day
```

- Put there by ADR 0007 (as `postbacks`). One row per accepted Lead or Purchase.
- Written by the postback endpoint after the signature, the timestamp, the fields and the click have been checked, and after the click's offer, looked up as `offers (clicks.catalog_version, clicks.offer_id)`, was found to belong to the partner in the path (Q-24). The insert is `INSERT ... ON CONFLICT (partner_id, type, transaction_id) DO NOTHING RETURNING id`; no row returned means a redelivery, answered `200` with `duplicate` (R-4, PB-5).
- `accepted_at` is the ordering key for "most recent Lead" (Q-10, ADR 0004). `occurred_at` is kept for reports and is not trusted for ordering, because it comes from a clock we do not control.
- `payout` is `REAL` in the MVP, where it is only displayed. The contract sends it as a decimal string; when EPU is computed from real data (DES-6), an integer column in minor units is added next to it.
- Counting rules, applied by queries and not by keys: one Lead per (user, offer) for metrics (Q-23), so a second Lead for the same user and offer with a new `transaction_id` is stored but counted once; a second Purchase with a new `transaction_id` counts (PB-5); a Purchase with no Lead for the same user and offer is counted and flagged by the same kind of query (Q-8). R-4's earlier idea of a Lead also unique per click is covered by the per-(user, offer) rule, which is broader.
- Read at entry and at completion as the user's Leads and Purchases, and by the report.

The query that finds the Leads at entry (decision table row 16, ADR 0004):

```sql
SELECT c.offer_id, v.accepted_at
FROM conversions v
JOIN clicks c ON c.click_id = v.click_id
WHERE c.user_id = ?1 AND v.type = 'lead';
```

`select()` keeps the Leads whose offer is active in the current version and orders them by `accepted_at` descending, then EPU, then offer ID.

### quarantine

```sql
CREATE TABLE quarantine (
  id             INTEGER PRIMARY KEY,
  partner_id     TEXT NOT NULL,
  type           TEXT,
  transaction_id TEXT,
  click_id       TEXT,          -- plain text on purpose: the click was not found
  body           TEXT NOT NULL, -- raw request body
  reason         TEXT NOT NULL, -- unknown_click
  received_at    INTEGER NOT NULL
);
```

- Put there by ADR 0007 (as `postback_quarantine`), for Q-11.
- Written by the postback endpoint when a correctly signed postback names a click ID that is not in `clicks`: a click removed by the cleanup, a partner integration error, or a forgery. The answer is `202`, so the partner stops retrying, and an alert fires on any new row.
- `click_id` has no foreign key, because the row exists exactly when the referenced click does not. A quarantined postback is never matched to a user by anything other than the click ID, is not counted, and emits no event.
- No unique key: a partner that redelivers an unknown-click postback adds a second row, which is harmless because nothing here is counted.
- Read by an operator. If the click turns out to exist after all, the postback can be resent through the normal endpoint.

### Cleanup and deletion

- The daily cleanup job (ADR 0003, Q-8, Q-16) deletes a user with no Lead and no Purchase whose last activity, the later of `last_completed_at` and the newest `clicks.created_at`, is older than 90 days. It deletes the user's clicks first, then the `users` row; `user_answers` go with it by cascade.
- A deletion request finds the user rows by `email_hash` and deletes them and their answers. Their clicks stay with `user_id` set to null, so revenue already counted does not change. Events in BigQuery carry the UserID but never the email; whether they must be deleted by UserID as well is part of Q-16.

### MVP events database

In the MVP a second D1 database stands in for BigQuery (ADR 0005). It has one table, `events`, with the envelope fields below as columns, `payload` as JSON text and `event_id TEXT PRIMARY KEY`. The loader inserts with `INSERT ... ON CONFLICT (event_id) DO NOTHING`, so a resent or redelivered event is stored once. It is a separate database so that its writes do not queue in front of selection, and it is removed when the loader targets BigQuery. It holds no facts and the rules never read it.

It has one index besides the primary key, `events_received_at ON events (received_at)`. Every report query filters on a `received_at` range, so rows read grow with the period asked for and not with the size of the table (R-17).

The size estimate in `nfr.md` assumed a D1 row for every user; since only users who complete the quiz now get rows, stage 4 revisits it.

## R2 layout

All event files live in the one bucket `funnels-events`. The keys are defined in `src/events/files.ts`. `<ms>` is the write time in Unix milliseconds padded to 13 digits, so key order is write order and the loader takes the oldest files first.

| Key | Written by | Content |
|---|---|---|
| `pending/<ms>-b-<uuid>.ndjson` | the Queue consumer | one batch of up to 100 events, one JSON object per line |
| `pending/<ms>-e-<event_id>.ndjson` | `sendEvent()`, when the Queue refuses | one event, one line |
| `batches/<batch_id>.json` | the loader | the manifest `{ batch_id, files, attempt, created_at }`; `batch_id` is the first 32 hex characters of SHA-256 over the sorted file keys joined by a newline |
| `loaded/<batch_id>.ndjson` | the loader | the rows inserted into D1 |
| `rejected/<batch_id>.ndjson` | the loader | the rows of a batch that failed five loads |
| `rejected/<batch_id>-invalid.ndjson` | the loader | raw lines that failed validation |
| `control/loader-paused` | an operator | the pause flag; the loader skips a run while it exists |
| `control/last-load.json` | the loader | `{ at, files, rows }` of the last run that loaded a batch |

Lifecycle: `loaded/` and `rejected/` expire after 30 days, through the bucket rules `loaded-30d` and `rejected-30d`. R2 lifecycle rules have no field in `wrangler.jsonc`, so they are applied once to the account with `wrangler r2 bucket lifecycle add`. Nothing deletes `pending/` or `batches/` automatically (ADR 0006).

Limits of one loader run in the MVP: at most 9,000 files, batches of at most 900 rows (100 insert statements of 9 rows), and at most 8 batches. That is at most 7,200 rows and 800 D1 queries, inside the 1,000 queries one Worker invocation may make. A file with more than 900 rows forms a batch of its own, and files are read 6 at a time.

## Current answers

In D1, the current answer to a question is the one row in `user_answers` for that user and question. It is written only from `POST /api/complete`, and a later completion replaces it only if its `received_at` is greater.

- Two tabs: the completion request received last wins (R-10, Q-4). Two completions with the same millisecond keep the one written first.
- One tab, back button, changed answer: the completion body is the state of the final screen, so the order in which step events reach the server cannot change what D1 stores (R-3). A step 2 answer stays valid when step 1 changes (Q-25); both are in the same body.
- The current quiz step is not stored anywhere (QZ-5). It can be derived from `step_viewed` events.

In BigQuery, the current answers of a user are the `answers` of that user's latest `quiz_completed` event by `received_at`. The `step_answered` events are the history of changes: a user who picked `asia`, went back and picked `europe` has two `step_answered` rows for `ethnicity` and one `quiz_completed` with `europe` (QZ-4). Answer distribution metrics read `quiz_completed`; answer change metrics read `step_answered`.

## Idempotency and ordering

| Case | Key or rule | Where |
|---|---|---|
| Browser resends an event (R-3) | `event_id` from the browser, kept on every resend | `events.event_id` primary key in the MVP; loader and view in BigQuery (ADR 0006) |
| Queue redelivers an event (R-8) | same `event_id` | same |
| Events arrive out of order (R-3) | analytics order by `received_at`, then `seq` within a visit; D1 does not depend on event order | event envelope |
| Completion request retried | the upserts write the same values again | `users`, `user_answers` |
| Two tabs complete the quiz (R-10, Q-4) | `WHERE excluded.received_at > user_answers.received_at` | `user_answers` |
| Partner redelivers a postback (R-4, PB-5) | `UNIQUE (partner_id, type, transaction_id)` | `conversions` |
| Second real Purchase (PB-5) | new `transaction_id`, so a new row, counted | `conversions` |
| Second Lead for the same user and offer (Q-23) | counted once per (user, offer) | report queries |
| Postback event queued twice | EventID derived from `(partner_id, type, transaction_id)` (ADR 0007) | event |
| Several Leads (Q-10) | `accepted_at` descending, then EPU, then offer ID | `select()` |
| Two catalog changes at once | `catalog_history.version` primary key | catalog script |

A retried completion emits `quiz_completed` and `offer_selected` again with new EventIDs. Metrics over these events count distinct users, and "current answers" takes the latest, so no number changes. A browser-generated completion ID would remove even these duplicates; it is listed under deferred options.

## Personal data

The email exists only in the body of `POST /api/complete` and, after that, in `users.email_enc` and `users.email_hash` (P-5, Q-16).

- `email_enc`: AES-GCM with a random IV, under a master key kept in a Worker secret. A database export or a Time Travel restore holds ciphertext only.
- `email_hash`: HMAC-SHA256 of the normalised email under a second, separate key, used for lookups. Without the key the hash cannot be checked against a list of known emails.

The event envelope has no field for the email, so `POST /api/events` cannot carry it as a field. As a backstop, the Worker validates the payload of every known event type (`step_answered` values must be allowed values from the question catalog). For every event, the producer also removes each payload key whose name contains `email`, at any depth, and logs how many it removed without any value, instead of rejecting the event. An email inside a string value, such as a page URL with `?email=`, is not removed: that is the accepted risk R-23.

The email must never appear in:

- URLs and query strings, including the `/go` link and the prelander URL;
- request logs (bodies are not logged) and error messages: the Worker logs "invalid email format", never the value;
- events, the Queue and R2 files;
- BigQuery and the MVP events database;
- partner redirect URLs and postbacks;
- the analytics report;
- the browser's localStorage: the browser keeps unsent events there, and the completion request is retried from memory, not from storage.

The log-scanning test runs the demo with `u1@example.com` and asserts that the address is absent from captured logs, URLs, Queue messages, R2 files and the events table (P-11, DEMO-8, R-12). The same check searches for the UserID (ADR 0002).

## Event catalog

### Envelope

Every event has the same envelope (ADR 0005). One event per request (Arthur's decision, 2026-11-02).

| Field | Set by | Meaning |
|---|---|---|
| `event_id` | browser for browser events (`crypto.randomUUID()`), Worker for server events | idempotency key (ADR 0002) |
| `schema_version` | whoever creates the event | version of this event's payload; an unknown version is passed through and never dropped |
| `type` | creator | one of the types below, or a new one |
| `client_time` | browser; null for server events | the browser's clock, for display only |
| `received_at` | Worker | server receive time; the ordering key for analytics |
| `user_id` | Worker, from the cookie; for `lead` and `purchase` from the click; null when the click's user was deleted | a `user_id` in the body is ignored |
| `visit_id` | Worker at entry, written into the page; browser repeats it | one load of the prelander (Q-26) |
| `seq` | browser, position in the visit starting at 1; null for server events | ordering within a visit |
| `prelander_id` | from the path at entry, from the request body or query otherwise, from the click for `lead` and `purchase` | breakdown by prelander (AN-2) |
| `payload` | creator | type-specific fields, a JSON column in BigQuery |

`POST /api/events` accepts browser types and unknown new types, and rejects the type names that only the server emits, so a client cannot post a `lead` or an `offer_click`.

### Types

| Type | Emitted by | Payload | Links to |
|---|---|---|---|
| `prelander_viewed` | server, `GET /p/{prelander}` | `reason`: `quiz`, `lead_return` or `skip` | prelander, visit. Only `reason = quiz` counts as a funnel start (Q-13, Q-21). `skip` is a rule 3 redirect at entry (Leads only for disabled offers, answers sufficient); its `offer_selected` carries the selection reason. |
| `step_viewed` | browser | `step` 1 to 3, `prefilled` (false; reserved for a prefill decision, Q-1) | visit; step 1 is "started the quiz" (Q-13) |
| `step_answered` | browser, steps 1 and 2 only | `step`, `question_key`, `value` | visit; history of answer changes (QZ-4) |
| `quiz_completed` | server, `POST /api/complete` | `answers` object, no email | visit; the current answers in BigQuery |
| `offer_selected` | server | `offer_id` (null for `no_offer`), `reason` (`lead_return`, `best_epu`, `fallback_universal`, `no_offer`), `moment` (`entry`, `completion`), `catalog_version` | offer, catalog version (P-3) |
| `offer_click` | server, `GET /go` or the entry redirect | `click_id`, `offer_id`, `catalog_version`, `reason` | click, offer, prelander |
| `lead` | server, accepted or duplicate postback | `click_id`, `offer_id`, `partner_id`, `transaction_id`, `occurred_at` (Unix milliseconds), `payout` (the partner's decimal string, or null), `currency` (ISO 4217, or null) | click, and through it the user, offer and prelander (PB-4, Q-22) |
| `purchase` | server, accepted or duplicate postback | same as `lead` | same |

`conversions.payout` stores the payout as a number (REAL), while the event carries the partner's string.

Step 3 has no browser answer event; finishing it is `quiz_completed`. A duplicate postback sends its `lead` or `purchase` again with the same EventID, derived from `(partner_id, type, transaction_id)`. If the Queue and R2 both refused the first send, the endpoint answered `503`, and the partner's retry is how the event reaches analytics; the events table keeps one row per EventID (ADR 0007). A quarantined postback sends nothing. `offer_selected` is emitted only when selection returns an offer or `no_offer`; an entry that shows the quiz emits `prelander_viewed` alone. `offer_click.reason` is the click's reason, added so BigQuery can tell a Lead return transition from a first one without reading D1.

### The nine events of a visit

A-1 sizes the design at nine events per visit, and the catalog gives the same count for a visit that goes through the quiz to an offer:

| Event | Count |
|---|---|
| `prelander_viewed` | 1 |
| `step_viewed` | 3 |
| `step_answered` | 2 |
| `quiz_completed` | 1 (stands for the third answer in A-1) |
| `offer_selected` | 1 |
| `offer_click` | 1 |
| Total | 9 |

`lead` and `purchase` are counted separately, as in A-1. A changed answer adds a `step_viewed` and a `step_answered`; A-1 leaves these out. A press on the offer button emits `offer_click` only, even when the catalog changed since the page was shown. A user who was shown one offer and went to another is found by comparing `offer_selected` (`completion`) with `offer_click` within one `visit_id`. A Lead return visit emits three events, so nine per visit is an upper bound and the load figures in `nfr.md` still hold.

## Change management

- Schema: numbered SQL migration files in the repository (`migrations/0001_init.sql`, `0002_...`), applied by `wrangler d1 migrations apply` in CI before the deploy. Migrations are additive only: new tables, new nullable columns, new indexes. Nothing is dropped or renamed in place. The migration runs before the new code is live, so the old code keeps working against the new schema for the minutes in between. A column that has to change is replaced by a new column that the code writes alongside the old one for one release.
- Events: `schema_version` on every event. A new payload field needs no table change in BigQuery (the `payload` column is JSON); a new envelope field is added by the load job (ADR 0006).
- Catalog: the version number on every click and every `offer_selected` event, so any past redirect is explained by the catalog it used (P-3).

To add something:

- A new offer: run the catalog script, which writes a new catalog version with the offer in it. No deploy.
- A new partner: insert one `partners` row with its encrypted secret and give the partner its secret. No deploy.
- A new prelander: its config and its page. No schema change; attribution works because every event and every click carries `prelander_id`.
- A new event type: send it from the client. The Worker and the loader already accept unknown types and versions; the report decides whether to use it.
- A new quiz question: a new step in the prelander's quiz flow config; the page renders from it. No migration, since `user_answers` is keyed by question.
- Offers restricted to a prelander: a `prelander_offers (prelander_id, offer_id)` table and one filter in the first step of `select()`, which receives the prelander as an input. A Lead return would then be filtered too, so a user with a Lead for an offer outside the new prelander's set would see the quiz there; whether that is wanted is a product decision.
- Offer exclusion after Purchase (DES-5, Q-20): the same first step of `select()` drops offers the user has a Purchase for, read from `conversions`. No new table is needed.

## Boundaries and deferred options

- Signed visit token. At entry the Worker would issue `visit_id` and `prelander_id` signed with HMAC, and every later request would carry the token. It would make the attribution of clicks to prelanders immune to client bugs. It costs one more secret, an HMAC check on every request, and a token to thread through the page; deferred until a wrong `prelander_id` is seen in the data.
- Completion ID. The browser could add a UUID to `POST /api/complete`, reused on retry, and the Worker could derive the EventIDs of `quiz_completed` and `offer_selected` from it, as ADR 0007 does for postbacks. Deferred because no metric changes without it.
- Rule sets per prelander. If prelanders need different selection rules, beyond a different set of offers, `select()` would branch on the prelander and the decision table would gain a prelander column.
- The catalog as its own service. If the catalog grows to hundreds of offers or gets an admin UI, it moves out, and D1 keeps a cached copy of the current version for selection.
- Prelanders on other registrable domains break identity: the same person gets a separate UserID there (R-1, R-2, Q-3).
- Facts only for completers. A user who leaves before the email step returns without a Lead and gets an empty quiz (Q-1). If the company asks for a prefilled quiz for such users, answers would have to be written to D1 before completion.
